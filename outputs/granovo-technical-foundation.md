# پایه‌ی فنی Granovo

## وضعیت فعلی

یک MVP اجرایی برای جریان تولید پیاده‌سازی شده است: حساب مستقل کارخانه، ثبت دستگاه و محدوده‌های مجاز، ثبت و ورود CSV بچ، داشبورد اپراتور، KPI وزن‌دار و پیشنهاد آزمایشی با تأیید اپراتور. لندینگ همچنان استاتیک است؛ فرم تماس آن فقط ایمیل آماده می‌کند و به دیتابیس متصل نیست.

کد API در `backend/`، داشبورد فارسی RTL در `landing/dashboard/` و تست‌ها در `tests/` قرار دارند. هیچ داده‌ی ساختگی در سامانه seed نمی‌شود.

## استک فعلی و مسیر توسعه

- **Frontend:** HTML/CSS/JavaScript بدون بیلد، داشبورد RTL در `/dashboard/` و لندینگ موجود
- **Backend:** FastAPI با API هم‌مبدأ، SQLAlchemy و اعتبارسنجی Pydantic
- **Database:** PostgreSQL با درایور psycopg؛ SQLite پیش‌فرض برای توسعه و تست محلی. تست‌های integration روی PostgreSQL 17 واقعی با socket ایزوله و SQLite پاس شده‌اند؛ پشتیبان‌گیری/بازیابی روی داده‌ی آزمایشی نیز تأیید شده است.
- **Authentication:** رمز scrypt، نشست ۱۲ساعته با مقدار هش‌شده در DB، کوکی HttpOnly/Secure/SameSite=Strict، بررسی Origin و CSRF برای نوشتن. هیچ کارخانه‌ای از طریق API به داده‌ی کارخانه‌ی دیگر دسترسی ندارد.
- **Rate limiting:** سقف ورود/ثبت‌نام در حافظه‌ی هر پردازش؛ استقرار چندپردازشی به limiter مشترک در لایه‌ی ورودی نیاز دارد.
- **Model:** رگرسیون ۳ همسایه‌ی نزدیک از بچ‌های تأییدشده‌ی همان دستگاه/پلیمر با نرخ رد زیر ۵٪؛ مدل صنعتی بهینه‌سازی نیست. حداقل ۸ نمونه لازم است؛ ورودی خارج از دامنه رد می‌شود. MAE روی holdout زمانی، نسخه‌ی داده و تأیید اپراتور ذخیره می‌شوند.
- **Later:** ذخیره‌ی تصاویر، تشخیص طیفی/بینایی ماشین، مدل صنعتی اعتبارسنجی‌شده، نقش‌های تیمی و اتصال به تجهیزات هنوز پیاده‌سازی نشده‌اند.

## مدل داده‌ی فعلی

- `factories`, `users`, `sessions`: هویت کارخانه و نشست‌های مستقل؛ ثبت‌نام همیشه کارخانه‌ی جدید می‌سازد، نه عضویت در کارخانه‌ی موجود
- `machines`: دستگاه و حدود دما، سرعت و فشار که کاربر از مشخصات تأییدشده وارد می‌کند
- `batches`: کد یکتا در کارخانه، تاریخ، دستگاه، اپراتور، مرحله‌ی baseline/pilot، پلیمر اصلی، خلوص، رطوبت، تنظیمات واقعی، تولید/مردود برحسب kg و وضعیت/عامل/زمان تأیید کیفیت
- `recommendations`: ورودی، خروجی، نسخه‌ی مدل، تعداد نمونه، خطای ارزیابی، درخواست‌کننده و عامل/زمان تأیید

ترکیب فعلی فقط پلیمر اصلی + خلوص + رطوبت است، نه فرمول چندجزئی. تأیید کیفیت یک تأیید دستی ثبت‌شده است، نه گواهی آزمایشگاهی. تأیید پیشنهاد فقط یک رکورد است و هیچ فرمانی به دستگاه ارسال نمی‌کند. تغییر داده‌ی آموزشی مانع تأیید پیشنهاد قدیمی می‌شود.

## KPI پایلوت

- نرخ رد کالا: `مقدار ردشده / کل تولید × ۱۰۰`
- خط مبنا: میانگین نرخ رد در حداقل ۴ هفته پیش از پایلوت
- هدف: کاهش نرخ رد به کمتر از ۵٪، بدون افت شاخص کیفیت توافق‌شده
- KPIهای کمکی: مصرف انرژی به ازای کیلوگرم، توقف خط، تعداد اصلاح دستی و زمان رسیدن به تنظیم پایدار
- گزارش‌دهی: مقایسه‌ی هفتگی خط مبنا با پایلوت و تفکیک بر اساس دستگاه و ترکیب ورودی

## اجرای برنامه و تست

```sh
python -m pip install -r requirements.txt
python -m backend.db
python -m backend
```

`python -m backend.db` فقط schema اولیه را با روش idempotent می‌سازد؛ ساختار دیتابیس موجود را migrate نمی‌کند. SQLite توسعه در فایل نادیده‌گرفته‌شده‌ی `granovo.db` است. برای PostgreSQL، `DATABASE_URL` را از تنظیمات امن استقرار با dialect `postgresql+psycopg` تنظیم کنید؛ مقادیر اتصال نباید در گیت ثبت شوند.

برنامه به‌طور پیش‌فرض روی loopback اجرا می‌شود و کوکی Secure دارد. برای production، پراکسی HTTPS هم‌مبدأ باید Host را حفظ و scheme را از loopback مورد اعتماد forward کند. گزینه‌ی `--allow-http` فقط برای توسعه‌ی محلی ایزوله است و نباید در production استفاده شود. این اجرا سرور دائمی یا استقرار انجام نمی‌دهد.

```sh
python -m pytest -q
node --test tests/dashboard.test.cjs
node --check landing/dashboard/dashboard.js
```

تست‌های backend با SQLite و PostgreSQL واقعی انجام شده‌اند؛ تست‌های داشبورد Node/VM هستند و مرورگر واقعی اجرا نمی‌کنند. موارد پوشش: ورود/خروج/انقضای نشست، CSRF، جداسازی کارخانه، اعتبارسنجی دستگاه/بچ، CSV اتمیک، ماندگاری DB، KPI وزن‌دار/روند روزانه و مرز ۵٪، gate داده‌ی مدل، نسخه و تأیید پیشنهاد، readiness با schema سالم/ناقص، نمایش امن متن و جریان ثبت‌نام/ثبت بچ در UI.

برای اجرای قابل‌تکرار PostgreSQL، ابزارهای initdb/pg_ctl/pg_dump/pg_restore/createdb باید نصب باشند:

```sh
python tests/run_postgres.py --bin-dir <postgres-bin-directory>
```

در نصب relocatable می‌توان `--share-dir` نیز داد. runner فقط cluster جدید زیر `.runtime/` می‌سازد؛ روی TCP گوش نمی‌دهد، socket فقط برای مالک قابل‌دسترسی است، به دیتابیس production وصل نمی‌شود و پس از تست و dump/restore با تأیید شمارش بچ‌ها، cluster را متوقف و حذف می‌کند. نتیجه‌ی این اجرا: ۳۲ تست backend روی دو دیتابیس و ۸ تست dashboard پاس شده‌اند. این تأیید backup روی داده‌ی آزمایشی است؛ زمان‌بندی، نگهداری و بازیابی backup واقعی production هنوز باید روی سرور تنظیم شود.

## قرارداد API

همه‌ی مسیرهای API جز ثبت‌نام/ورود نیازمند نشست‌اند؛ `/health` و `/ready` عمومی‌اند و هیچ جزئیات اتصال یا داده‌ای نمی‌دهند. نوشتن به `X-CSRF-Token` برگشتی از نشست نیاز دارد.

| مسیر | کاربرد |
|---|---|
| `POST /api/register`, `POST /api/login` | ساخت کارخانه‌ی مستقل یا ورود |
| `GET /api/session`, `POST /api/logout` | بازیابی/تازه‌سازی CSRF و ابطال نشست |
| `GET/POST /api/machines` | فهرست یا ثبت دستگاه |
| `GET/POST /api/batches` | ثبت و تاریخچه؛ فیلترهای machine_id/start/end؛ حداکثر ۲۰۰ ردیف همراه total |
| `PATCH /api/batches/{id}/quality` | تأیید/لغو تأیید دستی کیفیت |
| `POST /api/batches/import` | UTF-8 CSV با `Content-Type: text/csv`؛ حداکثر ۵۰۰ ردیف/۱MB؛ تراکنش همه یا هیچ |
| `GET /api/kpis` | KPI تمام رکوردهای فیلترشده و آرایه‌ی daily با تاریخ/مرحله، count، total_kg، rejected_kg و reject_pct؛ نه فقط ۲۰۰ ردیف تاریخچه |
| `GET/POST /api/recommendations` | ۵۰ پیشنهاد اخیر یا محاسبه‌ی پیشنهاد جدید |
| `POST /api/recommendations/{id}/approve` | تأیید صریح؛ بدون اعمال تنظیمات روی دستگاه |
| `GET /health` | سلامت پردازش؛ تضمین سلامت دیتابیس نیست |
| `GET /ready` | بررسی اتصال و تمام جدول‌های schema؛ وضعیت ready یا پاسخ عمومی ۵۰۳ در صورت نقص |

قالب CSV از داشبورد دریافت می‌شود و ستون‌های دقیق آن عبارت‌اند از:

```text
machine_id,polymer,purity_pct,moisture_pct,code,produced_on,phase,temperature_c,screw_rpm,pressure_bar,total_kg,rejected_kg
```

تاریخ `YYYY-MM-DD`، مرحله `baseline` یا `pilot` و پلیمر یکی از PE/PP/PET/PS/PVC/ABS است. داده‌ی واردشده خودکار تأیید کیفیت نمی‌شود.

## گیت‌های انتشار

PostgreSQL واقعی، restore آزمایشی، کنترل‌های احراز هویت/CSRF/جداسازی کارخانه و readiness بررسی شده‌اند. پیش از production: اتصال سرور پروژه، HTTPS، backup واقعی، کنترل نرخ مشترک و فرآیند تأیید کیفیت هنوز لازم است. دسترسی SSH این اجرا آماده نیست؛ وضعیت اتصال سرور باید در پنل بررسی شود. تست بصری مرورگر در این محیط مجاز نیست و باید دستی انجام شود. مدل صنعتی به داده‌ی واقعی و پایلوت نیاز دارد؛ هیچ نتیجه‌ی میدانی یا انتقال وجهی در این اجرا تولید نشده است.
